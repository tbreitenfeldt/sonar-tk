    State

    Bases: ABC

    Abstract base class for state machine states.

    States implement a three-phase lifecycle: setup, update, and exit. Each phase returns a boolean to allow conditional control flow. States are managed by StateMachine instances and can represent UI screens, game modes, menu systems, or any other discrete application state.

    State Transition Semantics

    When transitioning from state A to state B via StateMachine.change():

    1. A.exit() is called first
    2. If False is returned, the transition is aborted and A remains active

    3. If True is returned, A has completed cleanup (handlers removed, etc.)

    4. B.setup() is called next

    5. If False is returned, B declines to activate but A has already exited
    6. If True is returned, the transition completes and B becomes active
    7. If an exception is raised, A has already exited and cannot be restored

    Critical Consideration: If exit() returns True but setup() subsequently returns False, the state machine remains referencing the old state, but that state's exit() cleanup has already executed. This can result in a partially-deactivated state (e.g., event handlers removed but state still logically "active").

    Recommended Patterns: - Make exit() conditional: Only perform cleanup and return True if the transition is guaranteed to succeed - Make cleanup reversible: Store state in exit() that allows setup() to restore the previous state if needed - Design states to be idempotent: Ensure states can handle being in a post-exit condition gracefully

        Safe Transition Checklist:
            1. Validate preconditions in setup() before expensive or irreversible work
            2. Keep setup()/exit() side effects narrow and predictable
            3. Perform state-local cleanup in exit() only when transition should proceed
            4. Return False from exit() for recoverable conditions where transition
                 would break user interaction
            5. Avoid relying on timing delays between exit() and setup(); use explicit
                 state transitions where possible

    speech_manager

    sonartk.util.speech_manager

    This module was created to manage speech actions and properties in a singalton fassion. Implementing a true singalton class in python is challenging and often not very readable, so module level variables are used with the name mangling convention to enforce they are not to be imported from the outside world.

    output(message, interrupt=False, log_message=True)

    Send a message to the active screen reader and optionally store it in history.

    silence()

    Stop current speech output on the active screen reader.

    get_current_screenreader()

    Return the currently selected accessible_output2 output instance.

    is_nvda_active()

    Return whether NVDA is the active screen reader output.

    is_jaws_active()

    Return whether JAWS is the active screen reader output.

    is_voiceover_active()

    Return whether VoiceOver is the active screen reader output.

    is_sapi_active()

    Return whether SAPI5 is the active screen reader output.

    clear_history()

    Clear all stored speech history and reset history navigation position.

    pop_last_message()

    Remove and return the most recent history message, if available.

    trim_old_history(message_count)

    Remove the oldest history entries up to the requested count.

    next_history()

    Move forward in speech history and return the current message.

    previous_history()

    Move backward in speech history and return the current message.

    navigate_to_end_of_history()

    Jump to the newest history message and return it.

    navigate_to_beginning_of_history()

    Jump to the oldest history message and return it.

    get_speech_history()

    Return the in-memory speech history list.
